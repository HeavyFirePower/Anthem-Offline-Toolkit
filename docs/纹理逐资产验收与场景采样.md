# Anthem 纹理逐资产验收、引用与场景采样

地板配置加入后，具名程序覆盖为 575 个 PS，至少有一种 RGBA 解释的图从 18 张增至 30 张。默认纹理哈希、图集帧矩形和 18 组双探针 UE 对照见[法线、图集与探针](法线方向与BC7材质.md)。下文保留前六组配置的分项统计。


## 从已经解包的安装开始

在含 `Run-Anthem.ps1` 的游戏目录运行。以下五个入口共用一个输出根目录。若使用本工作区已经生成的结果，将 `$dst` 设置为 `E:\TitanExclusion\Tools\Anthem\output\texture-coverage`，可直接运行最后一条查询。

```powershell
$dst = Join-Path $PWD 'output/texture-coverage'
.\Run-Anthem.ps1 -Mode TexturePixels -Destination $dst
.\Run-Anthem.ps1 -Mode TextureConsumers -Destination $dst
.\Run-Anthem.ps1 -Mode TextureVariants -Destination $dst -ImportUE
.\Run-Anthem.ps1 -Mode TextureVisual -Destination $dst -ImportUE
.\Run-Anthem.ps1 -Mode TextureLookup -Destination $dst -All
.\Run-Anthem.ps1 -Mode TextureLookup -Destination $dst -Match 'vfx/textures/shared/vfx_rain_tile'
```

`TexturePixels` 和 `TextureConsumers` 均为全目录操作。只想手动导出一张图，仍可直接用 `-Mode Texture -Match 完整路径` 得到 DDS 与通道预览。`TextureVisual` 和 `TextureVariants` 可分别运行，前者处理关卡反射盒与加载图，后者处理雨幕、Strider、藤叶和 Spacebear 材质。省略 `-ImportUE` 可只生成源侧证据。`TextureVariants` 的源程序回放需要 Windows D3D11 设备。随包提供 x64 校验 DLL 和回放 EXE，日常使用无需编译。

## 每个纹理版本验证了什么

本安装有 246,332 条目录记录、23,673 个逻辑名和 24,414 个不同纹理头。24,414 个头各有一份完整内容，全部通过原始 chunk 与导出 DDS 的像素比较，共计 185,138 个平面、86,040,243,228 个纹素、304,338,298,039 个参与比较的解码字节。重复的 bundle 目录记录映射回同一份验收。对 MES_005 的立方体另做反向测试，改动最终面最小 mip 的一个字节和截短源 chunk 都被校验器检出。

| 维度 | 通过的不同版本 | 验收平面数 |
| --- | ---: | ---: |
| 2D | 17,074 | 138,833 |
| 2DArray | 5,275 | 32,063 |
| Cube | 2,050 | 13,530 |
| 3D | 15 | 712 |

`pixel-assets.sqlite` 的 `asset` 表保留目录 ID、逻辑名、RID 和纹理头 SHA-256。每份不同的头分别解析尺寸、格式、sRGB、mip、面及层数，通过 GUID 和完整字节长度选择 chunk 并核对其 SHA-256。同一逻辑名若有多个版本，查询会全部列出。

原始像素与导出 DDS 通过两条寻址路径比较。第一条从源 chunk 按 mip、面或数组层、Z 切片取数据。第二条写出标准 DDS，再由 DirectXTex 从内存载入，按 mip、item、slice 重新定位。块压缩面分别解码后逐字节比较；未压缩面按源精度比较，包括浮点、打包格式和 D16。对每个内容版本记录解码后的 SHA-256、纹素数、平面数与字节数。压缩两侧使用同一版本 DirectXTex，这个实验检验导出布局与解码后像素的保持程度。UE 资产重开的原始像素对照覆盖另行抽取的 28 张、146 级 mip。[DirectXTex 纹理操作](https://github.com/Microsoft/DirectXTex/wiki/DirectXTex)

每个格式与维度的分组及异常清单保存在 `pixel-audit.json`。再次运行可复用相同目录索引、DDS 导出／寻址代码和校验 DLL 下的成功记录。报告保存相应代码摘要。原始文件另有改动、需要重新核对其哈希时，指定新的输出目录。1D、1DArray、CubeArray、BC2 和有符号 BC6H 在此次安装中没有验收样本。

## 反查纹理的使用者

本次扫描覆盖 1,050,190 条 EBX 目录记录，按哈希读取 214,529 份独立内容，导入表和字符串表解析错误为 0。23,673 个纹理名中，23,231 个有直接导入或完整路径证据；442 个在这两种入口均未命中。模型外命中 17,052 个不同纹理名。下表的导入数包含多 RID 候选，行间的纹理名称可重叠。

| 使用者与证据 | 边数 | 使用者内容数 | 不同纹理名 |
| --- | ---: | ---: | ---: |
| 模型外 EBX，文件 GUID＋对象 GUID | 163,405 | 20,352 | 16,489 |
| 模型外 EBX，精确路径字符串 | 3,458 | 250 | 767 |
| 与 MeshSet 同名的 EBX，文件 GUID＋对象 GUID | 36,082 | 6,315 | 8,561 |

模型外的导入候选边包括 `vfx/` 17,401 条、`levels/` 15,665 条、`ui/` 10,346 条。按类型与槽位核实的例子包括 MES_005 反射层的 BakedTexture，以及 PC 按钮背景的九宫格贴图。其他目录前缀和字符串统计可查 `consumer-audit.json`。

`texture-consumers.sqlite` 扫描目录中状态正常的 EBX，按源 SHA-256 去重读取。精确匹配导入表里的 **文件 GUID 与对象 GUID**，并保留目标 TextureAsset 对应的 RES RID。第二条线索为源字符串表内与纹理完整逻辑路径匹配的字符串，大小写按游戏路径归一。字符串与所有者自己同名时从消费者视图剔除。字符串命中表示在此处出现了路径；要确认字段的用途还要追具体类型与偏移。

`TextureLookup` 接受完整逻辑名或单个 `-AssetId`。输出含内容版本、存储分量、所有者名和哈希、导入索引或字符串字节偏移，以及候选 shader 状态、指令行和经程序核对的 RGBA 用途。已有 `TextureMaterial -All` 的结果时，查询也会带入每个已知模型材质槽和候选 RID。没有程序证据的字段留空。本轮汇总的“模型以外”指逻辑名未与 MeshSet 同名的 EBX，包含 UI、关卡、材质变体等所有者。

`TextureConsumers` 还会建立全库 EBX 的导入／导出对象索引 `texture-graph.sqlite`。查询的 `upstream_ebx` 给出上游所有者、导入位置、目标文件 GUID 和对象 GUID。默认追溯两层，`-ReferenceDepth 3` 可继续向上，`-ReferenceDepth 1` 只看直接所有者。每层记录新到达的文件及其最短依赖边，避免重复遍历环。中间资产可能包含多个对象，导入表只能证明文件依赖；精确到字段的关卡路径见 `mes005_volume_chains`。未解析的导出布局、图集子矩形、纯哈希引用和运行时换绑仍会限制完整性。

跨 EBX 对象图收录 1,483,674 个导入表项和 834,744 个具名导出对象记录。1,483,478 个导入项在本库至少匹配一个完整文件／对象 GUID 对，196 个未匹配。1,749 份内容的完整导出布局未通过，其中 1,748 份仍能通过根对象偏移提取根 GUID。这些数值为整个 EBX 图的统计，包含非纹理依赖。

纹理对象表有 23,650 对文件／对象 GUID，可关联到 23,652 个逻辑纹理名，另有 21 个名称在这张表中没有对象对应。725 对 GUID 在同一名称下有多个 RID，17 对 GUID 对应多个名称。`ambiguous_texture_objects` 列出与所查纹理相关的全部候选；跨布局的直接导入边可能有多解，要确定某一版本仍须核对 bundle。

`TextureLookup -All` 生成 `texture-coverage.jsonl`，每个逻辑名一行，记录后缀、存储格式与维度、通过的像素版本数、直接使用者、已知槽位、候选与已解释的 PS 数量。缺少逐程序证据的纹理标记为 `unknown`。有对应程序的纹理也只在已列出的用法下确认通道，仍可能有其他用途。`coverage-summary.json` 给出各状态的数量。

```sql
SELECT owner,kind,at,rid FROM consumers
WHERE texture='ui/loading/textures/loadscreen_forttarsis'
ORDER BY owner,kind,at;
```

## 雨幕、Strider 与藤叶怎样读通道

从角色以外的实例提取了两套证据。Strider 厨房桌网格在 Patch 全局材质库有 2 个表面键、120 个候选状态和 36 个不同 PS。天气雨幕圆柱在 Data 的同 bundle 局部库有 1 个表面键、8 个候选状态、2 个不同 PS。按完整程序哈希保存反汇编和状态、材质对象、纹理目标的对应关系。共记录 269 条具名纹理访问。寄存器写入掩码与纹理操作数的 swizzle 一起决定实际取出的通道；程序获取分量之后，还要看这些分量参与的运算。

| 程序与槽位 | 有证据的分量与用途 |
| --- | --- |
| Strider 状态 29205 的 `Trim_Parallax_mask` | 指向 `sdr_str_cockpit_decalsheet_01_disp`。采样指令写 `r0.z`，纹理操作数为 `t5.yzxw`，取到 R。程序用 `2R−1` 和视差尺度偏移 UV。 |
| 同状态的 `Trim_Normal`、`Trim_EFFX` | 法线取 R、G、A，以 R×A 重建 X，以 G 重建 Y。特效图将 RGB 乘 A 后求和并乘发光强度，调制发光颜色。 |
| 同状态的 `Trim_Diffuse`、`Trim_AMMS` | Diffuse 的 RGB 与背景层按 A 混合。AMMS 的 R、G 参与照明与反射率计算，B、A 经混合后分别进入金属遮罩与平滑度对应输出。对声明 Trim_AMMS 的 17 个 PS 逐一检查，10 个读取 RGBA，4 个读取 RA，3 个读取 RBA。 |
| Strider 状态 6118 的 `Base_Diffuse`、`Base_AMMS` | 两个实例分别指向 dashmetal、rawmetal 的实际纹理。Diffuse 取 RGB，与积雪颜色混合写 o1.xyz。AMMS 的 R 缩放间接光；R×G 经 `0.5 × saturate(1.4 × R × G)` 与积雪层混合写反射率；B 和 A 分别混合到金属遮罩 o2.y 和平滑度 o0.z。 |
| 雨幕状态 49 的 `Diff_01`、`Diff_02` | 两个槽位指向同一张 `vfx_rain_tile`，以不同的平铺和随时间变化的 UV 采样。两条点积都获取 RGB，数据库保存的选择值均为 (1, 0, 0)，因此当前材质配置使用 R。 |
| 雨幕状态 49 的 `Mask_01` | 也指向同一张图。程序获取 RGBA 并做四分量点积。数据库默认选 R，实例 EBX 覆盖为 (0, 1, 0, 0)，因此在这个实例中 G 调制透明度。另一个 PS 多用一组插值颜色与透明度，其存在不能说明游戏某一历史帧选中了它。 |
| 藤叶状态 322 的 `NOT_Mask` | `fld_fol_ivyatlas_02_not` 的 R、G 经 2x−1 得到切线空间法线 X、Y，与常量 Z=1 一起经基变换并归一化。B 经重映射写反射率输出 o2.z，另以 0.46 为下限调制间接光。A 参与叶片换色权重，并分别与 `SSSR_SSST` 的两个参数计算 o2.x、o2.y。 |
| 藤叶状态 322 与 475 的 `BaseColor` | 同一张 `fld_fol_ivyatlas_02_diffa` 在 322 中提供基础色 RGB，A 在两个 Smoothness 端点之间插值。在 475 中程序只读取 A，小于 0.2 时丢弃像素，保留的值写入 RT0。这两个用途都有对应的完整 PS 哈希。 |

同一套工具再核对了 Data 的 Strider（80 个状态、14 个 PS）和 Patch 的雨幕（8 个状态、2 个 PS）。Patch 教程关卡的藤叶网格 `fld_fol_vinesfat_2x4c_mesh` 的一个表面 ID 在全局库中命中 5,532 个状态、116 个不同 PS。110 个程序有具名 NOT_Mask 读取，其中 88 个取 RGBA、14 个取 BA、7 个取 RGA、1 个只取 A。表面键的匹配数体现可选范围，不能由此确定实际帧使用的 pass。

可从 `MaterialTrace` 报告取一份材质所有者的 EBX ID 和选定 IShaderDatabase 的目录 ID，自行扩充程序索引。在 `TextureVariants` 上指定 `-OwnerId <完整EBX_ID> -DatabaseId <完整数据库_ID>`。工具检查同 bundle 的 MeshVariationDatabase 和全局或局部库范围，将所有匹配 PS 的指令和槽位写入 `variants/custom`，再次运行 `TextureLookup` 即可看到。自动分析提供程序实际读取的分量，人工复核过的用途另列在 `reviewed_rgba`。自定义所有者的 UE 材质仍需按程序实现。

Spacebear 的 72 条变体记录中有 19 个不同的外部材质覆盖对象，均已按文件和对象 GUID 唯一解析。查询保存各表面 ID、变体哈希、覆盖来源及对应候选状态。既有的状态 15745 接入相同的反查入口，覆盖身体 Diffuse、Normal、OSM、EFC 和甲壳虹彩渐变图。另核对了毛发状态 1729，`sbr_spacebear_hair_norm` 的 X 为 2RA−1、Y 为 2G−1，Z 由平方和开方重建，程序跳过 B。六份所有者／库配置合计 36,560 条候选记录，按程序字节去重为 449 个 PS、4,748 条具名纹理访问。18 张实际绑定的纹理具有至少一种已逐通道核对的程序用法；其余名称仍可查询像素、格式和已识别使用者。

雨幕在 D3D11 上执行原始 PS，再在 UE 5.8.4 重开生成的材质，在相同纹理、光照、深度、相机距离和点采样条件下比较首个输出目标 RGBA。时间输入为 0、0.137、0.413 秒，3×64×64 共 12,288 个像素。最大绝对分量误差 9.10×10⁻¹³。后两帧相对首帧分别有 24、22 个像素的 alpha 变化超过 0.001。控制输入和全部实例／数据库参数见 `variants/rain/rain.json`，逐帧指标见相邻 `visual-render.json`。这一组时间和相机参数由实验指定。原作每帧的绑定、覆盖值、深度和曝光仍缺少记录。

## 立方体方向、场景位置与成品图

关卡间接引用可沿两个真实对象数组复查。昼夜各自的 SubWorldData.Objects 含 LayerReferenceObjectData，其 Blueprint 字段指向反射层的文件 GUID 和根对象 GUID。LayerData.Objects 再定位各反射盒，BakedTexture 指向导出的 TextureAsset。82 个反射盒均通过 RID 唯一连到对应的纹理内容版本，共 82 张。该昼夜样本中的两层 BlueprintTransform 均为单位变换。用 `TextureLookup` 查询这些图，可在 `mes005_volume_chains` 读到父关卡、数组序号、盒对象和资源 ID。

MES_005 昼夜两个关卡层各解析出 41 个 PbrBoxReflectionVolumeEntityData。每项保留关卡 EBX、对象索引、源空间变换、LocalOffset、CaptureDistance，以及 BakedTexture 指向的对象。实测立方体由日间层对象 8 的 BakedTexture 直接引用，捕获距离字段为 130 m。盒的源位置约为 (−2616.49, 3441.33, −2233.46) m，三个轴存在非均匀缩放，局部 X 轴相对源水平轴旋转约 35°。日夜两层全部 82 个对象的 BakedGBuffer 内三项指针均为空。详细证据保存在 `visual/volume-placements.json`。

在 UE 中用真实 128×128 RGBA16F 立方体创建 `M_cube`。世界轴模式按本项目坐标换算，将 UE 方向 (X,Y,Z) 映为源方向 (X,Z,Y)。盒局部模式另外用该对象的三个归一化基向量做逆旋转。两种模式各取六面、每面五个不对称位置和 mip 0、2，重开编辑器从浮点渲染目标分别读取 RGB 和 alpha。120 个方向的 RGBA 均与对应源纹素一致。两种模式供检查烘焙方向；游戏运行时在该反射盒采用哪一种投影、是否施加视差修正或混合邻近探针，仍无同镜头帧可证。[Microsoft DDS 立方体面顺序](https://learn.microsoft.com/en-us/windows/win32/direct3ddds/dds-file-layout-for-cubic-environment-maps) · [Epic 向量与立方体采样](https://dev.epicgames.com/documentation/unreal-engine/vector-operation-material-expressions-in-unreal-engine)

Fort Tarsis 的配置 `configurations/ui/loadingscreensources/loadscreens_tarsis` 在字符串表字节偏移 448 保存了 `UI/Loading/Textures/LoadScreen_FortTarsis`。对这张 728×868、BC1 的实物图，先解码 DDS，再用 UE 的同尺寸无光照材质逐像素回读。全部 631,904 个像素的 RGB 和 alpha 均在 0.001 内，最大误差 2.97×10⁻⁸。此处对照对象是安装包中的成品加载图。相同相机下实时场景的光照、雾、反射、曝光和后处理仍未验证。保存的三个材质和三张纹理位于 `/Game/AnthemValidation/TextureVisual`。

`visual/screen-comparison.png` 从左至右显示原始加载图、UE 材质实际回读的 RGB、RGBA 误差超过 0.001 的像素位置。第三栏黑色表示该像素四个分量都通过，洋红色表示至少一个分量超过阈值。

## 重编译校验工具

`tools/texture_pixels.cpp` 使用微软 `directxtex_desktop_win10` 2026.5.8.1 x64 Release。解压该 NuGet 包到 `output/DirectXTex-sdk`，用 Visual Studio 的 x64 Native Tools 命令提示符从工具根目录运行。已有 DLL 的 SHA-256 随每次报告保存。[Microsoft DirectXTex 包](https://www.nuget.org/packages/directxtex_desktop_win10/2026.5.8.1)

```bat
cl /nologo /O2 /EHsc /std:c++17 /MD /DNOMINMAX /LD /Ioutput\DirectXTex-sdk\include tools\texture_pixels.cpp /Fooutput\texture_pixels.obj /link /OUT:tools\texture_pixels.dll /IMPLIB:output\texture_pixels.lib output\DirectXTex-sdk\native\lib\x64\Release\DirectXTex.lib bcrypt.lib ole32.lib windowscodecs.lib d3d11.lib dxguid.lib
cl /nologo /O2 /EHsc /std:c++17 tools\rain_replay.cpp /Fooutput\rain_replay.obj /Fetools\rain_replay.exe /link d3d11.lib d3dcompiler.lib
```
