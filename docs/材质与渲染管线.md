# Anthem 材质与渲染管线离线分析

停服后的可用证据来自安装文件：EBX、RES、Chunk、Shader 数据库和编译程序。当前可验证资源内容、纹理格式、部分顶点布局和 Shader 运算；没有原作运行时的常量值、帧事件顺序和对照画面，因此不能给出可信的视觉还原百分比。

## 本次已经证实的结果

游戏自带 Oodle 库可以解压本安装的样本。已选资源覆盖刚性/蒙皮 MeshSet、动画轨道、地形、音频、图集/字体、特效和 Shader 数据。`catalog.sqlite` 保存原始 RES 类型编号、RID、meta、GUID、CAS 路径/偏移和引用来源。

64 个 Shader 容器通过结构检查，并由微软 D3DDisassemble 成功反汇编；其中 60 个 VS 5.0、4 个 PS 5.0。这个样本不是整套渲染管线的统计抽样，不能用阶段比例估计游戏的运行时工作量。

以下证据保存在 `output/sample/shaders`：

| 证据 | 能确认的内容 | 不能据此确认 |
| --- | --- | --- |
| `.dxbc` 与数据库来源偏移 | 编译程序、输入输出签名、部分反射字段 | 原始编辑器节点、原始 HLSL、运行时选中哪个变体 |
| `reflection_report.json` | 常量缓冲字段名、字节偏移、大小；声明的纹理/采样器寄存器 | 每帧真实参数值、寄存器对应的具体纹理资产 |
| `69f47e6d…ecff2.asm` | Normal 纹理解码、4 个颜色输出、实例向量缓冲计算 | 每个 RT 的实际像素格式和整条管线用途 |
| `272518a8…5648e.asm` | forwardShadingPreIntegratedFG、室外阴影纹理等绑定声明 | 最终场景使用的实际光照强度、阴影设置、曝光 |
| 其他 VS 的反射 | 云空气透视、参与介质散射/透射体积等声明 | 这些资源在该帧是否执行、来自哪个 pass |

可推断样本包含面向多渲染目标的材质输出及前向光照相关变体；完整延迟/前向混合方式、pass 顺序、GBuffer 格式、TAA/后处理实现仍待数据库映射和更多 Shader 分析。声明存在不代表该资源在每个变体都被实际采样。

## 一个已经落到指令级的法线例子

样本 `69f47e6d8191066ed2d12897a85cd63c62660d6a19cc76bbf41dbf43db1ecff2` 的 PS 在 t1 绑定名为 `texture_Normal` 的二维纹理。采样和 swizzle 后，指令对应：

```hlsl
float2 xy = float2(sample.r * sample.a, sample.g) * 2.0 - 1.0;
float z = sqrt(max(0.0, 1.0 - dot(xy, xy)));
float3 tangentNormal = float3(xy, z);
```

后续用三个插值向量分别 dot，再归一化。不能未经基底定义就把这些向量称为 UE 的标准 TBN。参考函数放在 `tools/shaders/AnthemSampleNormal.hlsl`，只适用于这个已分析变体。

同一程序还有基于视线与法线点积的四次幂混合，实际表达式包含 `1.001` 偏移和上界 1。还把某个采样的 alpha 输出到 `o0.z`，把另两个通道经过缩放/偏移写到 `o2.yz`。这些输出是继续追踪解码端 Shader 的线索，不能直接命名为 roughness/metallic。

这个例子说明：只把一张“normal”接到 UE Normal，或者按文件名把 OSM 接成 ORM，可能改变算法。应先追踪具体指令、采样器和通道的使用，再定义材质函数。

## 纹理保持策略

完整纹理目录覆盖 18 个源格式编号、4 个维度。4096×4096 的 `sbr_spacebear_jungle_a_osm` 在头中是 BC1_SRGB。一个命名为 OSM_Mask 的程序会重映射 R 和 G，B 还影响平滑度端点。Spacebear 已查到真实的材质槽与纹理 RID，默认身体现已按 SurfaceShaderId 找到 3,780 条编译状态及 30 个不同 PS，离屏回放已覆盖其中一个。各后缀的实际绑定及 13 个像素程序的逐通道证据见[纹理格式与 RGBA 通道](纹理格式与RGBA通道.md)。

两张流式纹理的完整数据来自 TOC 资源，单独提取 bundle chunk 会漏高 mip。完整 mip 总长度、GUID、分块范围和解压长度应同时匹配；`first_mip` 不能直接被解释为“整个纹理只有剩余低 mip”。

源 DDS 保存原始像素块。纹理研究工具另导出完整解码 DDS 供 UE 使用，已从保存的 UTexture.Source 重新读取并比对全部样本的所有 mip 与面／切片。TGA 用于二维预览。运行时派生纹理的压缩、法线基底和着色器通道混合仍须分别验证。

## 材质依赖解析的下一层

优先建立下列关系，并对每条边存储证据来源，而不是只保存一个最终贴图路径：

1. 网格 section/material ID 对应的 EBX 材质和实例/variation。
2. 材质参数或着色器图到 RES RID、Shader 数据库和程序变体。
3. 变体的 texture/constant/sampler 槽位到具体纹理、参数值及渲染状态。
4. 纹理头到 chunk；完整 mip、sRGB、UV 集、采样模式与解码函数。
5. 顶点流到 VS 输入，包括切线压缩、顶点色、额外 UV、实例数据及蒙皮。

已检查本安装的 9 个 F7／F9 材质库和两个系统程序库。材质对象可按 bundle 和布局追到候选状态、编译程序和部分参数，Spacebear 保留已验证的全纹理表面实例。另有离屏可执行的间接光照、屏幕空间皮下扩散及漫射合成。逐帧运行时选择和完整场景光照仍未知。[Spacebear 材质实例](材质实例变体与UE像素对照.md) · [F7／F9 与光照、皮下散射](材质数据库光照与皮下散射.md)

Data/Patch 不能简单按资产名字覆盖。相同名字、GUID 或 Shader hash 可能在不同 bundle 上下文使用；工具保留多个候选。用于重建时应按目标 bundle 的补丁覆盖关系解析依赖，并把无法消除的歧义留在报告中。

## UE 5.8.4 中的实现边界

| 还原层 | 处理方式 | 验收方法 |
| --- | --- | --- |
| 数据 | 原 BC、mip、尺寸、sRGB、参数类型和单位不丢失 | 字节长度、哈希、元数据比较 |
| 材质运算 | 按字节码恢复通道运算、UV 变换、法线解码、层混合、透明裁剪 | 对固定输入向量做数值比较 |
| 顶点行为 | 切线基、风摆、蒙皮、实例参数、视差或位移 | 对固定顶点/骨骼姿态比较输出 |
| 光照模型 | 比对 Fresnel、分布/可见性函数、能量补偿、漫反射及特殊材质 | BRDF 曲线、白炉测试、固定灯光球体 |
| 管线 | GBuffer 编解码、Decal、体积、阴影、IBL、曝光/色调映射 | 独立数值和受控场景验证；原作画面对比当前不可用 |

普通材质图可以表达的运算优先用 Material Function；复杂函数可用 HLSL。若 UE 默认着色模型的光照积分或 GBuffer 语义不同，单个 Custom 节点不能替换整套光照管线。是否采用 Substrate 或引擎着色模型扩展，必须在实际 BRDF 和数据布局确认后决定。

先关闭会掩盖误差的自动曝光、动态后处理和随机变化，建立固定灯光/固定相机的测试场景。Lumen、Nanite 和 UE 后处理是目标引擎能力，不能自动当作 Frostbite 原管线的等价实现。第一轮验证应区分“材质函数一致”和“最终画面接近”。

## 建议的后续验收单元

每次完成一种材质家族，如硬表面涂装、布料、皮肤、植被、水、地形混合或半透明粒子，保存一个可复现的证据包：原始资产 ID、程序 hash、纹理 GUID、输入参数、函数源码、数值测试、UE 渲染配置和当前未知项。

停止使用“感觉相近”作为最高还原度依据。已经确定的字段写为原值，推断字段单独标记；未知值保留未知。停服情况下可提高静态算法与数据的一致性，但无法证明历史运行时所有参数和最终画面的完全一致。
